# Rule: 3.2 Memory and Data Model

**Stage:** 3 — Architecture Specification

## Slots
Purpose · Contents · Gate · Boundary · Bridge

## Purpose
How the system holds/serves data Tool Contracts read/write, including caching obligations where used.

## Required sections
1. Memory architecture overview
2. Data entities
3. Data schemas
4. Engineering and run artifact store (not SRS deployable registry)
5. Memory access patterns
6. Context management (Domain Model grounded; windowed/bounded; injected into runs)
7. Persistence strategy
8. Data integrity rules
9. Data lifecycle management
10. Caching requirements (tiers; TTL; invalidation; must/must-not; TC-aligned) — or explicit no-cache + justification

**Out (do not include):** TC detail, Domain Model ontology, CA topology, EG control flow, ABS/prompts/code, TLA+ dynamics, SRS deployable registry

## Artifact acceptance gate
All answers must be YES to approve:
1. Accepted Tool Contracts version named?
2. How data is held stated (entities, schemas, persistence including engineering/run artifact store)?
3. How data is accessed stated (architecture, patterns, context with domain grounding)?
4. Caching requirements stated (or explicit no-cache + justification)?

## Boundary
Data plane for TC reads/writes; not control-flow topology.

## Bridge
→ Execution Graph Specification.
